# 지도 렌더링 프로토타입 — 검증 결과

검증일: 2026-09-18
검증 대상: PLAN.md v3 §13 "MapLibre에서 229개 지역에 각각 다른 사진 텍스처를 입히고 60fps 줌이 나오는가"

## 결론

**된다. 단, 방식이 하나뿐이다 — 아틀라스(단일 합성 텍스처) 방식.**
"지역마다 텍스처 하나씩" 방식은 250개 지역에서 메모리 197MB로 모바일에서 쓸 수 없다.

---

## 1. 기법 검증

### 채택: 캔버스 클리핑 + 메르카토르 정렬 georeferenced 텍스처
1. 오프스크린 캔버스에 지역 폴리곤 경로를 `clip('evenodd')` (구멍 처리 포함)
2. 그 안에 사진을 cover-fit으로 그림 → 지역 밖은 투명
3. 캔버스를 지리좌표 4모서리에 매핑해 소스로 등록

**필수 조건**: x는 `lon × π/180`, y는 `ln(tan(π/4 + lat×π/360))` — **둘을 같은 단위로 맞춰야 한다.**
경도는 도, y는 메르카토르 단위로 섞어 쓰면 종횡비가 60배 틀어져 사진이 세로로 뭉개진다. (첫 시도에서 실제로 발생)

### 기각: `fill-pattern`
MapLibre의 fill-pattern은 이미지를 **화면 픽셀 기준으로 반복 타일링**한다. 폴리곤에 고정되지 않아
줌하면 사진이 따라오지 않고 벽지처럼 미끄러진다. "부산 모양으로 잘린 부산 사진"을 만들 수 없다.

---

## 2. 성능 실측

측정 환경: macOS / Chromium / MapLibre GL JS 4.7.1 / 캔버스 2048×1536(DPR 2)
측정 방법: `map._render()` 후 `gl.readPixels()`로 GPU까지 강제 동기화한 프레임 시간.
카메라 4지점(전국 z6.2 / 수도권 z10.2 / 피치 38° z11 / 부산 z9.4) × 20프레임 = 80프레임.

| 방식 | 지역 수 | 소스/레이어 | 텍스처 메모리 | 프레임 중앙값 | p95 | 최대 |
|---|---:|---:|---:|---:|---:|---:|
| 단색 (경쟁사 방식) | 250 | 0 / 1 | — | **3.2 ms** | 3.7 | 4.2 |
| **아틀라스** | 90 | **1 / 1** | **59.6 MB** | **3.4 ms** | 3.8 | 5.5 |
| **아틀라스** | 250 | **1 / 1** | **59.6 MB** | **3.4 ms** | 3.7 | 4.2 |
| 개별 텍스처 | 90 | 90 / 90 | 70.7 MB | 5.6 ms | 6.2 | 10.3 |
| 개별 텍스처 | 250 | 250 / 250 | **197.0 MB** | 7.0 ms | 9.3 | 11.3 |

### 핵심 발견

1. **사진 채우기는 공짜다.** 아틀라스 3.4ms vs 단색 3.2ms — 차이 0.2ms.
   경쟁사의 단색 칠하기와 **사실상 동일한 비용으로** 사진 지도를 그릴 수 있다.
2. **아틀라스는 지역 수에 영향을 받지 않는다.** 90개든 250개든 1소스/1레이어/59.6MB로 고정.
   커버리지가 올라가도 성능이 나빠지지 않는다 — 이게 결정적이다.
3. **개별 텍스처 방식은 탈락.** 250지역에서 프레임 2배, 메모리 3.3배.
   197MB는 중급 안드로이드에서 텍스처 예산을 통째로 잡아먹는다.
4. 합성 비용: 최초 146ms(이미지 디코드 포함), 이후 재합성 10~37ms. 사진 교체 시 체감 지연 없음.

## 3. 해상도 한계 (LOD 경계 확정)

4096px 아틀라스로 국토 전체(경도 약 7.5°)를 덮으면 **z9 부근이 한계**다.

→ PLAN v3 §9의 LOD 설계와 정확히 맞물린다:
```

z10+    해당 지역만 고해상도 재합성  ← 추가 구현 필요
z11+    장소 핀으로 전환            ← 원 설계대로
```
z10 이상에서 화면에 보이는 시·도만 별도 아틀라스로 재합성하면 메모리를 늘리지 않고 해결된다.

## 5. 시각 검증

- **다크 테마가 명확히 우세.** 라이트에서는 사진이 배경에 떠 보이고 경계가 흐려진다. PLAN §9의 "다크 기본" 판단이 맞았다.
- **바다/육지 대비는 원안이 틀렸다.** 미방문 육지를 배경과 거의 같은 톤(#16181F on #0E0F13)으로 깔았더니
  채운 곳은 잘 떠오르지만 **국토 윤곽 자체가 사라져** 지도가 검은 덩어리로 보였다.
  3단계를 비교해 `중`으로 확정 — 바다는 더 어둡게(#0A0B0F), 육지는 더 밝게(#1E212B), 경계선 0.08 → 0.15.
  한쪽만 조정하지 않고 **양방향으로 벌리는 것**이 핵심이다.
  `강`(경계선 0.22 이상)은 격자가 도드라져 "딱딱한 행정지도" 인상으로 되돌아간다 — 상한선.
  육지 톤은 중립 회색이 아니라 살짝 푸른 회색이다. 중립 회색은 따뜻한 사진 옆에서 탁해 보인다.
- **커버리지 100%에서는 콜라주가 과해진다.** 서로 다른 사진 250장이 붙으면 톤 통일 레이어(7%)만으로는 부족.
  → 커버리지가 높은 유저에게는 채도를 더 눌러주는 보정이 추가로 필요하다.
- 경쟁사 방식(단색)과 나란히 놓으면 차이가 설명이 필요 없을 만큼 크다.

## 6. 남은 리스크 — 이 결과가 그대로 이전되지 않는 부분

1. **측정 환경이 웹이다.** MapLibre **GL JS** / Chromium / Mac 기준이다.
   실제 앱은 MapLibre **GL Native** / 중급 안드로이드다. 절대 수치는 이전되지 않는다.
   다만 **상대 비교(아틀라스 ≈ 단색, 개별 = 2배/3.3배)와 메모리 수치는 이전된다.**
2. **`canvas` 소스 타입은 GL Native에 없다.** 웹에서는 캔버스를 직접 소스로 쓸 수 있지만,
   React Native에서는 `ImageSource`(4모서리 좌표)로 넣어야 한다.
   → 오프스크린 합성을 네이티브에서 해야 한다 (react-native-skia 등). **이 부분은 별도 검증 필요.**
3. 저사양 기기의 텍스처 업로드 시간(59.6MB 단일 텍스처)은 측정하지 못했다.
   → 4096 대신 2048(15MB)로 낮췄을 때의 화질 손실과 함께 실기기에서 재볼 것.

# 2차 검증 — 장소 핀 레이어 (2026-09-18)

## 발단: 폴리곤 사진만으로는 제품이 성립하지 않는다

1차 프로토타입은 폴리곤 레이어만 검증했다. 실제 커버리지로 띄워놓고 보니
**시·군·구 하나 = 사진 한 장은 정보량이 사실상 0**이었다.
해운대구 전체가 카페 사진 한 장으로 칠해져 있으면 "부산 어딘가에 이런 게 있다"밖에 말하지 못한다.

그런데 이 앱의 핵심 가치는 *"인터넷에서 본 그 여행지가 여기였구나"* 다.
**그건 폴리곤이 아니라 핀이 전달한다.**

→ 폴리곤 사진의 역할을 **"저줌 요약 / 커버리지 성취감"** 으로 강등하고,
   **장소 핀을 정보 전달의 본체**로 재배치했다.

## 검증 데이터 — 실제 한국 POI

OpenStreetMap(Overpass API)에서 실제 좌표·상호명을 받아 사용. 키 불필요, 라이선스 ODbL.

| 구분 | 수 |
|---|---:|
| 전체 POI | **7,561** |
| 관광(attraction/viewpoint/museum 등) | 3,512 |
| 맛집 | 3,224 |
| 카페 | 564 |
| 술집 | 151 |
| 해변 | 110 |
| 시·군·구 매칭 성공 | 6,858 / 7,561 (245개 지역) |

실제로 렌더되는 이름: 해운대 일대 기준 — 주천조각보박물관, 추리문학관, 해월전망대,
청사포다릿돌전망대, 모루씨 해리단길, 미포경북횟집, 스타벅스 신세계마린시티점 등.

## 확정된 LOD

```
z ≤ 8.6     폴리곤 사진 (국토 요약 / 내가 칠한 범위)
z 8.6–9.4   폴리곤 페이드아웃          ← 겹치는 구간을 최소화해야 탁해지지 않는다
z 9.6–11    클러스터 (개수 표시)
z 11–12     개별 핀 (사진 썸네일 + 카테고리 링)
z ≥ 12      상호명 라벨 등장
```
클러스터 설정: `clusterMaxZoom: 11`, `clusterRadius: 68`

## 성능 (1차와 동일한 방법: `_render` + `readPixels` 강제 동기화)

| 구성 | 프레임 중앙값 | p95 | 최대 |
|---|---:|---:|---:|
| 핀 끔 | 2.7 ms | 4.3 | 4.5 |
| **핀 켬 (7,561 POI + 240 아이콘)** | **3.7 ms** | 5.6 | 9.5 |

핀 레이어 추가 비용은 프레임당 약 1ms. 아이콘 텍스처 240장(80px) ≈ 6.1MB 추가.
아틀라스 59.6MB와 합쳐도 66MB 수준으로 예산 안에 있다.

## 구현 함정 3가지 (전부 실제로 겪음)

**1. 카테고리 링을 별도 circle 레이어로 두면 안 된다.**
`icon-allow-overlap:false`로 아이콘이 충돌 제거되어도 **circle 레이어는 충돌 처리를 하지 않아
링만 남는다.** 화면이 색 덩어리로 덮였다.
→ 링을 아이콘 이미지에 직접 구워야 한다. 사진 48장 × 카테고리 5종 = 240개 아이콘을 사전 등록.

**2. 아이콘 레이어와 라벨 레이어를 분리하면 안 된다.**
두 심볼 레이어가 서로 충돌 처리를 해서 **라벨이 아이콘을 밀어낸다.**
라벨만 뜨고 썸네일이 사라지는 현상이 나왔다.
→ 하나의 symbol 레이어에 `icon-image` + `text-field`를 함께 둔다.

**3. `text-field`의 줌 임계값은 반드시 정수여야 한다.**
심볼 레이아웃은 **타일의 정수 줌**에서 평가된다. `['step',['zoom'],'',12.4,...]`로 두면
z12 타일에서 항상 빈 문자열이 되어 z12~13 구간에서 라벨이 아예 뜨지 않는다.
→ 임계값 12. 부드러운 등장은 `text-opacity` 보간으로 따로 처리한다.

## 카테고리 팔레트

맛집이 전체의 43%라 화면을 뒤덮는다. **가장 강하게 눌러야 하는 색이 가장 흔한 색이다.**

```
관광 #7FA8C4   해변 #6FB5B3   맛집 #C98A6E   카페 #BCA07C   술집 #9D89B5
```
전부 채도를 낮춘 값이다. 경쟁사의 형광 원색과 정반대 방향.

## 남은 판단 — 폴리곤 사진의 최종 역할

핀이 정보를 전달하게 된 이상, 폴리곤 사진을 어디까지 유지할지는 제품 결정이다.
- (A) 현행 — 저줌에서만 사진, 확대하면 핀으로 인계
- (B) 폴리곤 사진 폐기 — 지역은 사진들의 평균색 틴트만, 정보는 전부 핀
- (C) 레이어별 분리 — `나의 기록`은 폴리곤 사진(성취/감성), `전체 공개`는 핀(정보)

## 주의

샘플 사진이 Lorem Picsum(무작위 사진)이라 **폴리곤의 미적 판단이 불리하게 왜곡된다.**
실제 한국 여행 사진으로 채우면 인상이 크게 달라질 수 있다. 최종 판단은 실제 사진으로 할 것.

# 3차 — 레이어 분리(C) + 뷰포트 연동 리스트 (2026-09-18)

## 확정: (C) 레이어별로 시각 언어를 분리한다

| 레이어 | 지도 | 목적 |
|---|---|---|
| 나의 기록 | **폴리곤 사진** + 커버리지 % | 성취·감상 |
| 우리 스페이스 | 폴리곤 사진 + 멤버 핀 | 함께 채운 범위 |
| 전체 공개 | **장소 핀만** (육지 평평) | 정보 탐색 |

폴리곤은 **범위**를 말하고 핀은 **장소**를 말한다. 한 화면에서 둘을 동시에 주장하면
서로를 방해하므로 레이어로 나눈다. `전체 공개`에서는 방문/미방문 구분이 의미 없어
육지를 평평하게 깐다.

## 뷰포트 연동 리스트

지도를 움직이면 **현재 화면 안의 장소만** 리스트에 남는다. (카카오맵·에어비앤비 패턴)

- 헤더 `전체 공개 · 화면 안 268곳` — 레이어명 + 화면 내 개수
- 카테고리 칩(전체/관광/해변/맛집/카페/술집)이 **지도와 리스트를 동시에** 필터링
- Peek = 가로 스크롤 카드 / Expanded = 세로 리스트(썸네일·상호명·카테고리·지역·반응수)
- 카드 탭 → 해당 핀으로 `flyTo`
- 정렬: 반응 수 내림차순. MVP는 이게 전부 (알고리즘 없음)

### 구현 노트
클러스터 개수가 필터를 반영해야 하므로, 레이어·카테고리 변경 시 **소스 데이터 자체를
`setData`로 갈아끼운다.** MapLibre 클러스터링은 레이어 `filter`로 걸러지지 않는다
(클러스터가 원본 전체로 미리 계산되기 때문).

## 성능

| 동작 | 시간 |
|---|---:|
| 뷰포트 필터 (7,561건 전수 스캔) | **0.3 ms** |
| 리스트 렌더 (카드 120장) | **2.0 ms** |
| 레이어 전환 (`setData` 포함) | **5.3 ms** |

`moveend`에 90ms 디바운스를 걸어두면 팬·줌 중에는 아무 비용도 들지 않는다.
7,561건 전수 스캔이 0.3ms라 공간 인덱스(R-tree 등)는 이 규모에서 불필요하다.

## 프로토타입 조작

- 상단 세그먼트: 레이어 전환
- 바텀시트 핸들: Peek ↔ Expanded
- 칩: 카테고리 필터
- 우상단 ⚙: 개발 패널(렌더 방식·대비·벤치마크) 열기/닫기 — 기본은 접힘

# 4차 — 렌즈 모델 교정 (2026-09-18)

## 무엇이 틀렸었나

3차의 `전체 공개 / 우리 스페이스 / 나의 기록` 세그먼트는 **층위가 다른 것을 한 줄에 놓았다.**

- `나의 기록` = **소유** 기준
- `전체 공개` = **공개 범위** 기준
- `우리 스페이스` = **소속** 기준

셋이 배타적이지 않다. **내 공개 기록은 `나의 기록`에도 `전체 공개`에도 속한다.**
데이터 모델(Pin은 user 소유 / PinSpace N:M / is_public)은 애초에 맞게 되어 있었고,
**UI 명명만 틀렸다.**

## 교정된 모델 — 축 3개를 분리

| 축 | 정체 | 어디서 |
|---|---|---|
| 소유·소속 | 누구 것이고 어느 폴더에 묶였나 | 데이터 |
| 공개 범위 | 누가 볼 수 있나 (복수 선택) | 데이터 |
| **렌즈** | 지금 지도에 무엇을 띄울까 | UI |

**모든 기록은 일단 내 것이다.** 공개 범위는 그 위에 얹히는 속성이지 별도 저장소가 아니다.

## 렌즈 = 드롭다운 (세그먼트가 아니다)

스페이스는 N개이므로 세그먼트로는 담을 수 없다.

```
[ 내 지도 ▼ ]
   ├ 내 지도                내 기록 전부
   ├ ─── 스페이스 ───
   │   제주 우정여행 2026   멤버 3명
   │   부모님과 남해        멤버 4명
   │   + 새 스페이스        여행 폴더 만들기
   └ 모두의 지도            전체 공개된 기록
```

프로토타입에 데모 플래그를 심어 축이 독립임을 확인했다:

| 렌즈 | 핀 수 |
|---|---:|
| 내 지도 | 582 |
| 제주 우정여행 2026 | 194 |
| 부모님과 남해 | 78 |
| 모두의 지도 | 7,270 |

스페이스 핀은 전부 `내 지도`에도 포함되고, 내 기록 중 공개분은 `모두의 지도`에도 포함된다.
**겹치는 것이 정상이다.**

## 부수적으로 잡은 버그

`circle-opacity`와 `circle-stroke-opacity`는 별개다. 클러스터를 줌으로 페이드시킬 때
stroke를 같이 처리하지 않으면 저줌에서 **테두리 타원만 남아 떠다닌다.**

## 프로토타입 조작 (갱신)

- 좌상단 드롭다운: 렌즈 전환 (내 지도 / 스페이스 / 모두의 지도)
- 바텀시트 핸들: Peek ↔ Expanded · 칩: 카테고리 필터
- 우상단 ⚙: 개발 패널 (렌더 방식 · 육지 대비 · FPS 벤치마크)

# 5차 — 밀집 지역 핀 도배 (2026-09-18)

## 문제

"장소당 핀 1개"여도 번화가는 도배된다. 실측:

| 화면 | 화면 안 장소 | 충돌 제거만 했을 때 |
|---|---:|---:|
| 강남 z13 | **1,748곳** | 썸네일 69개 |
| 해운대 z12 | 444곳 | 40개 |
| 강릉 z13 | 116곳 | 16개 |

MapLibre의 `icon-allow-overlap:false`가 이미 대부분 걸러내지만 부족하다.
69개도 도배로 보이고, **나머지 1,679곳은 흔적조차 없어 "여기 더 있다"를 알 수 없다.**

## 해법 — 3단 표현

| 단계 | 표현 | 역할 |
|---|---|---|
| 상위 N개 | 사진 썸네일 + 상호명 | "볼 만한 곳" |
| 그다음 전부 | 작은 카테고리 점 (2~4px) | "여기도 뭐 있음" |
| — | 리스트에만 | 정확한 목록 |

`N = z<12 → 10 · z<14 → 16 · z≥14 → 24`

### 핵심: 순위는 뷰포트 안에서만 매긴다
전역 순위를 쓰면 강남(1,748곳) 기준에 밀려 **강릉(116곳)에는 아무것도 안 뜬다.**
`moveend` 디바운스 180ms에 뷰포트 랭킹을 다시 계산하고 `rk` 속성으로 `setData`한다.

### 결과
| 화면 | 썸네일 | 점 |
|---|---:|---:|
| 강남 z13 | **10** | 1,752 |
| 해운대 z13 | **12** | 88 |
| 강릉 z13 | **10** | 100 |

## 예상 밖의 수확

점이 노이즈가 아니라 **정보**였다. 강남에서 점들이 테헤란로 축을 따라 늘어선 모습이
"여기 상권이 이렇게 뻗어 있구나"를 한눈에 보여준다.
썸네일만 있을 때는 절대 보이지 않던 층위다.

> **지도에 전부 그리려는 것이 욕심이었다.**
> 지도는 "어디에 뭐가 몰려 있는지"를, 정확한 목록은 뷰포트 리스트가 담당한다.

# 6차 — 수계 + 프로필 지도 (2026-09-18)

## 강·하천을 넣어야 지도가 읽힌다

행정경계만으로는 "그냥 땅 덩어리"다. 강남구를 보고 있어도 여기가 어디인지 모른다.
**한강이 보이는 순간 "강 남쪽"이 즉시 읽힌다.**

| 항목 | 값 |
|---|---|
| 수면 폴리곤 (호수·저수지·넓은 강) | 650개 · 점 136,664 → 12,144 |
| 하천 중심선 | 1,400개 · 점 197,949 → 25,673 |
| 파일 | 997 KB |
| 출처 | OSM `natural=water` + `waterway=river` (ODbL) |

### 함정 2개

**1. 한강 본류는 `["name"]` 조건으로 못 가져온다.**
한강은 이름 없는 way 조각들이 relation(멀티폴리곤)으로 묶인 형태다.
이름을 요구하면 통째로 빠진다. → **둘레 길이(`if:length()>6000`)로 걸러야 한다.**
그래도 폴리곤으로는 안 잡혀서 결국 `waterway=river` **중심선**을 따로 받아 합쳤다.
오히려 중심선이 국토의 '혈관'을 보여줘서 방향 감각에 더 좋았다.

**2. 수계 색은 육지보다 명도·색상을 둘 다 벌려야 한다.**
처음 `#1A2436`(육지 `#282B36`)으로 했더니 거의 보이지 않았다.
`#0E182E`로 어둡고 푸르게 내리자 비로소 읽혔다.

하천 굵기는 길이 3등급 × 줌 보간. 한강은 z16에서 34px, 지류는 6px.

## `@누구의 지도` — 개인 프로필 지도

피드에서 사진 한 장을 보고 작성자로 들어가면 **그 사람의 여행 지도가 통째로** 열린다.

```
내 지도     = 내 기록 전부        (나만)
@나의 지도  = 내 기록 중 공개분만  (누구나)
```

**같은 지도인데 보는 주체에 따라 내용이 다르다.** 프로토타입 실측:

| 렌즈 | 장소 수 |
|---|---:|
| 내 지도 (내가 봄 · 전부) | **1,261** |
| @minji의 지도 (남이 봄 · 공개분) | **757** |
| @dohyun의 지도 | 1,092 |
| 모두의 지도 | 6,385 |

별도 저장소가 필요 없다. **같은 데이터에 `is_public` 필터 하나를 더 거는 것뿐이다.**

진입점은 리스트 카드의 작성자명(`@minji`). 탭하면 렌즈가 바뀐다.
드롭다운에도 `프로필 (공개분만)` 섹션으로 노출했다.

# 7차 — 검색 · 기준점 · 거리 (2026-09-18)

## 빠져 있던 것

와이어프레임에는 🔍 검색과 📍 내 위치 버튼이 처음부터 있었는데
프로토타입에 구현하지 않았다. 지도 렌더링 검증에만 집중한 누락이다.

## 기준점(Anchor) — GPS를 일반화

**여행 중에는 내 현재 위치보다 숙소가 더 중요한 기준일 때가 많다.**
그래서 GPS를 특별 취급하지 않고 기준점의 한 종류로 다룬다.

지정 방법 4가지: 📍 내 위치 · 검색 결과의 `[기준]` · 핀 상세 · 지도 롱프레스(600ms)

기준점이 정해지면 거리·소요시간 표시, 반경 필터(500m/1km/3km), 가까운순 정렬이 켜진다.

### 실측 (해운대 숙소 기준 반경 1km)
```
45곳
씨라이프 부산 아쿠아리움  100m · 도보 1분
스타벅스                130m · 도보 2분
MIX                    140m · 도보 2분
Namaste                190m · 도보 3분
```

### 거리 표기 규칙
```
< 1km    10m 단위 반올림      "130m"
≥ 1km    소수 1자리           "1.4km"
≤ 1.2km  "도보 N분" (4.5km/h)
> 1.2km  "차 N분"
```
**1.2km를 넘으면 걷는 거리로 읽히지 않는다.** 여행자는 도보 20분을 걷지 않으므로 차로 바꿔 말한다.

## 검색 — 지역과 장소를 한 입력창에서

별도 탭 없이 지도 위 돋보기 하나. 시·군·구와 POI를 한 결과에 섞는다.
**한 행에 두 동작**: 행을 누르면 이동, `[기준]`을 누르면 기준점 지정.
장소 결과에는 썸네일을 붙인다 — 이름만으로는 "이쁜지"를 모른다.

## 구현 노트

- 반경 원은 GeoJSON 폴리곤을 직접 생성(64각형). 위도 보정 필요:
  `dLng = r/(111320·cos(lat))`
- 반경 필터는 `visiblePois`(리스트)와 `refreshPoi`(지도 소스) **양쪽에** 걸어야 한다.
  한쪽만 걸면 지도와 리스트가 어긋난다
- geolocation 실패·거부 대비 폴백은 필수. 프로토타입은 해운대 데모 좌표로 떨어진다

## 범위에서 뺀 것

**실시간 경로 안내는 만들지 않는다.** 길찾기는 지도앱이 이미 잘한다.
우리는 "어디 갈지 정하는 것"까지만 책임지고, 결정 직후 네이버지도로 넘긴다.

# 8차 — 클러스터를 사진으로 (2026-09-18)

## 문제

숫자만 들어간 흰 원이 깔리니 **부동산 앱처럼 읽혔다.**
이 앱은 "얼마나 있나"가 아니라 **"어떤 곳인가"를 먼저 말해야 한다.**

## 해법

클러스터 = 그 묶음에서 **반응이 가장 좋은 장소의 사진** + 오른쪽 위 개수 배지.

- 아이콘 크기는 개수에 비례: 2곳 34px → 20곳 45px → 200곳 58px → 1000곳 72px
- **배지는 3곳 이상일 때만.** 2곳짜리에 붙이면 사진보다 배지가 커 보인다
- 클러스터 테두리는 **중립 흰색** — 카테고리가 섞여 있으므로. 카테고리 색은 개별 핀에만

## 구현 트릭 — 대표 사진 고르기

MapLibre `clusterProperties`는 **누적 연산(max/sum/min)만** 지원한다.
"가장 반응 좋은 멤버의 사진"을 직접 뽑는 방법이 없다.

→ **두 값을 한 숫자에 인코딩해서 `max`를 취한다.**

```js
clusterProperties: { top: ['max', ['+', ['*', ['get','likes'], 100], ['get','imgi']]] }
// top = likes×100 + imgIndex   (imgIndex < 100)
// 복원: likes = ⌊top/100⌋,  imgIndex = top % 100
layout: { 'icon-image': ['concat','phc',['to-string',['%',['get','top'],100]]] }
```

max가 likes를 우선하므로 **자동으로 가장 반응 좋은 멤버의 사진**이 뽑힌다.

## 배지 위치의 한계

`circle-translate`는 **데이터 기반 표현식을 지원하지 않는다**(줌 표현식만 가능).
그래서 배지 오프셋을 클러스터 크기에 비례시킬 수 없어 고정값 `[13,-13]`을 썼다.
큰 클러스터에서 배지가 약간 안쪽에 앉지만 앱 아이콘 배지와 같은 형태라 어색하지 않다.
정확히 맞추려면 배지를 symbol 레이어로 바꿔 `icon-offset`(데이터 기반 지원)을 써야 한다.

# 9차 — 실제 한국 여행 사진으로 미감 재판단 (2026-09-18)

1~8차 내내 샘플이 Lorem Picsum 무작위 사진(사람 얼굴·사물·외국 건물)이라
**폴리곤 미감 판단이 불리하게 왜곡돼 있었다.** 실제 한국 여행지 사진으로 교체해 다시 봤다.

## 데이터

| 항목 | 값 |
|---|---|
| 출처 | **위키미디어 공용** (Commons API, 키 불필요) |
| 장수 | **131장** · 42MB |
| 라이선스 | CC BY-SA 4.0 (45) · CC0 (34) · CC BY-SA 3.0 (14) · CC BY-SA 2.0 (13) · 그 외 |
| 장면 | 풍경·명소 97 · 해변 19 · 음식 10 · 카페 5 |
| 지역 | 서울 21 · 부산 19 · 제주 15 · 경주 10 · 속초 10 · 강릉 10 · 통영·여수·전주·안동 각 5 |

수집 카테고리: 해운대 · 광안리 · 감천문화마을 · 부산타워 · 경복궁 · 북촌한옥마을 · N서울타워 ·
청계천 · 한강 · 성산일출봉 · 한라산 · 불국사 · 첨성대 · 전주한옥마을 · 하회마을 · 설악산 ·

> 키워드 검색은 쓸 수 없다. "해운대"로 검색하면 **화재 사고 보도 사진**이 상위에 나온다.
> 큐레이션된 **Category**를 쓰고, 가로형(1.15~2.4) · 900px 이상만 걸러야 한다.

## 결론 — 인상이 결정적으로 달라진다

**폴리곤 콜라주가 조화로워졌다.** 5차에서 "커버리지 100%면 콜라주가 과하다"고 적었는데,
그 원인의 상당 부분이 사진의 성격이었다.

- **Picsum**: 사람 얼굴 · 사물 클로즈업 · 추상 이미지가 섞여 시선이 찢어진다
- **실제 여행 사진**: 한옥 처마 · 바다 · 산 · 야경 — 피사체 거리와 색온도가 비슷해 **자연히 묶인다**

→ §9의 "톤 통일 오버레이 7%"는 여전히 유효하지만, **근본은 사진 성격의 일관성**이다.
그리고 실서비스에서는 유저가 올리는 것이 애초에 여행 사진이므로 이 조건이 자동으로 충족된다.

## 두 가지를 더 고쳐야 했다

**1. 폴리곤 사진을 순번대로 배정하면 안 된다.**
`imgs[idx % imgs.length]`로 넣었더니 전라도 타일에 서울 사진이 들어가 설득력이 무너졌다.
→ **지역 인지 배정**: 사진의 지역 키워드를 시·도명/시군구명과 부분 일치시킨다.
`부산`→`부산광역시`, `경주`→`경주시`, `전주`→`전주시완산구`. 매칭 실패 시 풍경 풀로 폴백.

**2. 폴리곤에는 풍경 사진만 넣는다.**
음식 클로즈업이 지역 폴리곤을 채우면 지도가 아니라 메뉴판이 된다.
→ 폴리곤 풀은 `sight`+`beach`만 (116장). §8.5 대책 2("대표 사진은 장면이어야 한다")와 같은 원리.

## 비용

| 항목 | 값 |
|---|---|
| 아이콘 텍스처 (131장 × 5카테고리 + 131 클러스터 = 786개) | **19.2 MB** |
| 국토 아틀라스 (4096×3825) | 59.8 MB |
| 합계 | **79 MB** |
| 아틀라스 재합성 (사진 131장 로드 후) | 357 ms |

2차에서 탈락시킨 "지역별 개별 텍스처" 방식의 197MB와 비교하면 여전히 여유가 있다.

## 남은 것

- 음식·카페 사진이 15장뿐이다. 위키미디어 특성상 상업 시설 사진이 적다.
  실서비스 비율(맛집 43%)과 다르지만, **대표 사진은 장면이어야 한다**는 정책상 오히려 방향은 맞다.
- 이전 샘플은 `photos_picsum_backup/`에 남겨두었다.

# 10차 — 폴리곤 한 장의 한계, 모자이크 분할 실험 (2026-09-18)

## 문제

"강릉에 열 번 갔어도 폴리곤은 항구 사진 **한 장**." 시·군·구 하나에 사진 하나라는 구조적 한계.

## 실험 — 기록 위치로 보로노이 분할

기록이 일정 수 이상인 지역을 **실제 기록 좌표를 씨앗으로 보로노이 분할**해
조각마다 다른 사진을 넣어 봤다. "많이 간 곳이 시각적으로도 풍성해진다"는 보상 설계.

구현: 보로노이 셀 = 이웃 씨앗과의 수직이등분선으로 자른 반평면들의 교집합(볼록다각형).
씨앗이 6개 이하라 Sutherland–Hodgman 반평면 클리핑으로 충분히 싸다.
캔버스의 연속 `clip()`이 교집합으로 동작하므로 `지역 ∩ 셀`이 그대로 나온다.

| 설정 | 결과 |
|---|---|
| 기록 4개 이상 · 최대 6조각 | 90개 지역 → **192조각** |
| 기록 8개 이상 · 최대 3조각 | 90개 지역 → **106조각** |

## 결론 — 기각. 정보량은 늘지만 미감이 떨어진다

**시·군·구 크기 대비 사진이 이미 작은데 더 쪼개면 각 사진이 "장면"으로 읽히지 않는다.**
3조각으로 줄여도 마찬가지였다. 하늘 한 조각, 바위 한 조각, 간판 한 조각이 되어
**사진이 아니라 파편**으로 보인다. 조각 경계가 직선이라 인위적인 인상도 준다.

→ 기본값 **끔**. 개발 패널에 토글로 남겨두었다(밀도를 원하는 사용자를 위한 옵션 가능성).

## 진짜 답 — **공간을 쪼개지 말고 시간으로 쪼갠다**

같은 폴리곤이 **언제를 보느냐에 따라 다른 사진**을 보여주면
정보량은 늘면서 사진 한 장의 크기와 미감은 그대로다.

1. **연도/여행 슬라이더** (이미 §6 계획) — 2019년을 보면 2019년 강릉, 2024년을 보면 그때 강릉
2. **폴리곤 탭 → 갤러리** (이미 §6 계획) — 그 지역 전체 사진 그리드로 진입
3. **사진 장수 배지** — 폴리곤 모서리에 `47` 같은 표시로 "한 장이 전부가 아님"을 알린다

공간 분할은 화면을 나누지만, 시간 분할은 **같은 화면을 다시 쓴다.** 후자가 맞다.

# 11차 — RN 이식 검증 (2026-09-18)

전체 결과는 `../rn-port/FINDINGS.md`. 요약만 남긴다.

## 결론: 이식 가능. 세 군데를 바꾼다

| | 웹 | RN |
|---|---|---|
| 아틀라스 | `{type:'canvas'}` | `<ImageSource url="file://…">` ★ canvas 소스 없음 |
| 오프스크린 합성 | `<canvas>` 2D | Skia `MakeOffscreen` |
| 아이콘 | `map.addImage()` | `<Images>` + `onImageMissing` 지연 생성 |
| 레이어 | `addLayer({type,layout,paint})` | `<Layer type layout paint>` — **거의 그대로** |

MapLibre RN **v11은 스타일 스펙을 그대로** 쓴다. 레이어 정의가 문자 그대로 옮겨진다.

## ★ `Images`와 `ImageSource`는 로딩 경로가 다르다

같은 라이브러리인데 이미지를 가져오는 네이티브 코드가 완전히 다르다.

- **`ImageSource`**: Android가 `java.net.URL`을 쓴다 → **`data:` URI가 예외를 내고 catch에서 삼켜진다.**
  지도에 아무것도 안 뜨고 에러도 안 난다. → **`file://` 필수**
- **`Images`**: Android는 Fresco, iOS는 RCTImageLoader → **`data:` 지원** → base64 그대로 OK

## 검증 범위

- 패키지 tarball을 받아 **TS 소스와 네이티브 구현(ObjC/Kotlin)을 직접 읽음**
- 이식 코드 517줄 작성 → **`tsc --noEmit` 오류 0**
- **네이티브 빌드·실기기 실행은 못 했다. 성능은 전혀 측정하지 못했다.**

## v10 기억으로 쓰면 전부 틀린다

`MapView`→`Map`, `ShapeSource shape`→`GeoJSONSource data`,
`FillLayer/LineLayer/…`→단일 `Layer`, `defaultSettings{centerCoordinate,zoomLevel}`→`initialViewState{center,zoom}`,
`getVisibleBounds()[[e,n],[w,s]]`→`getBounds()[w,s,e,n]`.
표현식 배열은 스펙 타입이 튜플이라 `as ExpressionSpecification` 캐스팅이 필요하다.

→ **"입력 0"을 포기하고 "1탭"을 목표로 바꿨다.**

④ 거리를 쓴다. **후보를 잘 정렬하는 것이 이 앱의 실제 기술 과제**가 됐다.

# 16차 — 후보 정렬 알고리즘 (2026-09-18)

"반경 50m 안에 31개"라는 15차의 문제를 **실측으로 풀었다.**

## 신호별 감소폭 (해운대구 적재대상 10,345건 · 400곳 표본)

| 조건 | 후보 중앙값 | ≤5개 |
|---|---:|---:|
| ① 반경 50m 단독 | **19개** | 14% |
| ② + 1층 | 17개 | 17% |
| ③ **+ 카테고리** | **6개** ★ | 44% |
| ④ + 1층 + 카테고리 | 5개 | 50% |
| ⑤ 반경 30m + 둘 다 | 3개 | 69% |

**카테고리가 압도적이다 — 3배 감소.** 1층은 단독으로는 거의 무의미(19→17)하고
카테고리와 결합할 때만 의미가 있다.

## ★ 그런데 둘 다 필터로 쓰면 안 된다

- **반경을 좁히면** GPS 오차(도심 10~30m)로 정답을 놓친다
- **카테고리를 필터로 쓰면** 사진 분류가 틀리는 순간 정답이 목록에서 사라진다

→ **반경은 넓게(150m), 좁히는 것은 정렬로.** 후보에서 빼지 않고 순서만 바꾼다.

```
score = 2.5 × 1/(1+거리/50)
      + 3.0 × (카테고리 일치 ? 분류신뢰도 : 0)
      + 0.6 × 1층
      + 2.0 × ln(1 + 그 좌표에서 이 장소가 선택된 횟수)   ← 시간이 지나면 최강
      + 0.3 × ln(1 + 인기도)
```

## 선택 이력이 진짜 해법이다

`place_picks(place_id, cell, pick_count)` — 100m 격자 단위로
**같은 건물에서 사람들이 실제로 무엇을 골랐는지** 누적한다.
콜드스타트에는 0이지만, 쌓이면 거리·카테고리보다 강해진다.
사용자가 고르는 순간 `api_record_pick()`으로 즉시 학습한다.
